# ELEVATORUPDATE — first working version

AutoCAD 2023, Windows x64, .NET Framework 4.8. Updates the existing `plan codex.dwg` geometry in the current drawing. It does not redraw the elevator from scratch.

**Run it**

1. Open `plan codex.dwg`, or a drawing previously generated by this command, in AutoCAD's Model tab.
2. Run `NETLOAD` and select `bin/ElevatorPlanGenerator.dll`. Do this once per AutoCAD session. AutoCAD may show its normal trusted-code loading prompt for this locally built DLL.
3. Run `ELEVATORUPDATE`.
4. Enter **SW**, then **SD**, in millimetres. These mean clear internal shaft width and depth. Enter accepts the current dimension shown as the default.

The command calculates the derived values, modifies the current drawing, and saves a uniquely named separate DWG under this project's `output` directory. It also writes a JSON calculation/dimension report with the same basename. It does not save over the input drawing. The generated drawing can be reopened and updated again.

No cabin, rail, counterweight, door, DBG or TZ values are requested from the user. `config/input.example.json` documents the two-value input shape; the normal command uses the two AutoCAD prompts and does not require editing a file.

**Implemented rules**

| Value | Rule |
|---|---|
| Car DBG | `SW - 2 * 150` |
| Car width | `Car DBG - 100` |
| Car depth | `SD - 125 - 150 - 125` |
| TZ | `Car depth / 2 + 150` |
| CW rail centreline depth | `SD - 125`, retaining the existing rear arrangement |
| Car rail centreline depth | `CW centreline - TZ`; with these rules, this equals the cabin depth midpoint |
| Cabin front | 125 behind the shaft inner entrance datum |
| CW DBG | Largest fitting value from `1040, 940, 900, 840, 800, 740, 700, 640, 600` |
| Door width | Largest fitting value from `600, 700, 800, 900, 1000` |

The first-version fit policy uses the existing template allowances:

- CW guide faces retain at least **205 mm per shaft side**. Thus a candidate CW DBG must be `<= SW - 410`. The CW plan outline is `CW DBG - 40` wide, retaining 20 mm between each frame end and opposing guide face. Its existing 100 mm depth and small vertex residuals are preserved.
- The door must leave at least **75 mm on each side inside the cabin**, and its existing **135 mm jamb detail per side** must fit within the shaft. Thus select the largest catalogue width satisfying `door <= car_width - 150` and `door + 270 <= SW`.
- The door and cabin remain centered. Cabinet/rail/frame positions follow the actual shaft-local reference frame.
- The existing governor, rail details and wall supports must fit inside the new shaft; a dimensionally invalid size is rejected before geometry changes. The lowest width admitted by this profile is 1150 mm. Depth fit also depends on the preserved equipment outlines.

These are plan-generation rules for this supplied equipment template. Counterweight sizing here means the 2D frame outline; mass, balancing, frame height, structural rail selection and equipment certification are outside this command.

For **SW=1450, SD=1600**, the result is:

| Output | mm |
|---|---:|
| Car DBG | 1150 |
| Car width × depth | 1050 × 1200 |
| CW DBG | 1040 |
| CW outline width × depth | 1000 × 100 |
| Door width | 900 |
| TZ | 750 |

A verified example is supplied at `output/Elevator_SW1450_SD1600.dwg`.

**Project separation**

| Part | Location |
|---|---|
| Drawing reader | `src/DrawingReader/DrawingReader.cs` |
| Elevator design rules | `src/ElevatorDesignRules/DesignRules.cs` |
| Geometry calculator | `src/GeometryCalculator/GeometryCalculator.cs` |
| AutoCAD updater and command | `src/AutoCADDrawingUpdater/` |
| Configuration and input schema | `config/` |

`equipment-profile.json` stores the supplied formulas' constants and the template fit policy. `template-bindings.json` explicitly binds all 521 source entities to functional roles and records their expected types/layers. The source handles bootstrap the first run; the command adds `ELEVATOR_PARAMETRIC` XData tags to retain role identity in generated drawings. Existing AutoCAD XData and dimension associations are retained.

The shaft origin and axes come from the existing inner outline and entrance datum. There are no fixed world coordinates in the implementation. In-plane movement and rotation were tested. The first version intentionally rejects a tilted/mirrored plane or a changed template topology/signature instead of guessing at replacements.

The updater stretches only mapped line/polyline spans. It translates rigid rail/profile/governor entities and their hatches together, handles the four wall-connected car-rail support lines separately, adjusts existing leaders, preserves text formatting and original Z values, and updates all 31 native dimensions. It does not purge, flatten, globally scale, or replace the original drawing with new linework. Unbound additional objects are left untouched.

**Build and tests**

Run `build.ps1` in PowerShell. It uses the installed AutoCAD 2023 assemblies and Windows .NET Framework C# compiler. No Python, external package restore, network service, or COM registration is needed to run the plug-in.

Run `tests/build-tests.ps1` for the 43 pure-rule assertions and to compile the AutoCAD integration helper. The integration scripts execute the real `ELEVATORUPDATE` prompts on a disposable source copy; test-only commands are in `ElevatorPlanGenerator.Tests.dll` and are not needed for normal use.

The final integration run passed seven updates, seven saved-DWG reopens, and two rejected inputs. It checked geometry against the original template, all 31 dimension formulas, colors/linetypes/lineweights, rigid profile preservation, hatch areas, entity count, repeated resizing, and a translated/rotated placement. See `TEST_RESULTS.md` and `tests/cad-test-results.json`.
