# L2b: the A0 geared sheet in the generated drawing (2026-10-12)

The AutoCAD adapter (`Elevator.AutoCAD/Sheet/SheetAssembler.cs`, called by the Core Console host after the four views are final) adds the
layout `SM_Geared_A0` of `Templates/Layout_Geared_A0.dxf` to the generated DWG, only when the generation request carries a `SheetRequest`
(the desktop always sends one; a request without it generates exactly what it did before).

| Step | What |
|---|---|
| Real extents | The AutoCAD geometric extents of each view's visible entities, dimensions and labels included (`GenerationResponse.Bounds`), plus a 40 mm margin |
| Arrangement | `SheetArrangement` (Core): the shaft plan leads, no other main view takes a larger scale; the reference details keep the scale their texts state |
| Layout | Cloned from the template (frame, `SM_TITLEBLOCK`, `SM_LOGO_AREA`); reference details cloned into model space at their offset (untagged) |
| Viewports | One per view, locked, standard scale, on layer `view port` (no plot), scale label "1:N" centred under each |
| Title block | `TitleBlockData.Attributes()`: Arabic in `SM_AR` (xarab, encoded by `XarabText`), English in `SM_EN` (cent) |
| Logo | A raster image linked to the company logo file, fitted in the `SM_LOGO_AREA` rectangle |
| Plot settings | `DWG To PDF.pc3`, ISO full bleed A0, `monochrome.ctb`, layout, 1:1 (set when the device is available) |

## What the check by eye found (for the Planner)

Passed: no viewport overlaps another; the title block is filled in every field; the Arabic company, owner, project, phase, drawing-name and
person texts read correctly (xarab, joined letters); P1-P7 are "P1 = 760 KG." as decided; the views are not changed (same entity counts and bounds
with and without the sheet).

Not good, and not fixed here (they belong to the template or to the views):

1. **The logo does not plot.** The image is in the DWG (`-IMAGE ?`: one definition, one instance, full path) but the AutoCAD Core Console writes no
   image into the PDF (the plotted PDF has no image object). The PDF route through Core Console therefore loses the logo. Options for L3:
   plot with the full AutoCAD, vectorise the logo into the DWG, or put the PNG onto the PDF afterwards (PyMuPDF / a PDF library).
2. **Values touch the static texts in the template's value cells.** "P5 = 1360 KG." runs into "IN CASE OF OPERATION OF THE"; the static bracket
   crosses the "KG." of P6 and P7; the date and phase values sit on their labels (التاريخ، المرحلة) in the bottom row. The attribute positions were
   drawn for a bare number, not "P1 = 545 KG." and a dd/MM/yyyy date.
3. **A long project name overflows its box** ("Villa bx12 - 2S-800-4-stops-1720x2800" runs over the frame). The attribute has a fixed height; it
   needs a width factor, a smaller height or two lines.
4. **The views carry their own scale texts**: "MACHINE ROOM 1:8", "SHAFT AND CAR 1:8", "SEC AT A-A 1:35", "SEC AT B-B 1:10" are drawn in model space
   and disagree with the real scale label under each viewport (1:10, 1:10, 1:50 / 1:75, 1:20). The view titles must be generated from the scale.
5. The 2S project fills 0.51 of the drawing area (the others 0.61-0.67): a larger shaft makes the plan 1:10 dominate and A-A is held at 1:50.
   The empty band lies centre-bottom; the generated details of the later step can use it.
6. The detail dimensions (`ISO-25`, `Standard` dimension styles) take the generated drawing's definition when the names clash; they look right in the
   four sheets but were not compared numerically.
