# ElevatorProject model — schema version 1

`Elevator.Core.Project.ElevatorProject` is the common input contract. It has ProjectInfo, ElevatorConfiguration, BuildingConfiguration, ShaftConfiguration, CarConfiguration, CounterweightConfiguration, DoorConfiguration, MachineConfiguration, SuspensionConfiguration, RailConfiguration, MachineRoomConfiguration, DrawingConfiguration and StandardsConfiguration groups. It has no AutoCAD object IDs, handles, document types or assembly references.

See CURRENT_INPUT_INVENTORY.md for every current input, unit, default, provenance, prompt and future UI mapping. `config/ElevatorProject.schema.json` describes the serialized shape; `examples/ElevatorProject.example.json` is generated by the round-trip test. The example includes an explicitly identified provisional source CW pose, not a new engineering recommendation.

## Authoritative inputs

The JSON envelope has integer `schemaVersion: 1` and `project`. Missing, fractional or unsupported envelope versions are rejected before typed deserialization. Serialization preserves Unicode project/floor names and extension dictionaries. This implementation targets .NET Framework 4.8 and uses the existing System.Web.Extensions JSON serializer; it runs in a standalone .NET Framework process without AutoCAD. A future .NET migration may replace this codec without changing domain ownership or the JSON contract. JSON enum values (LegacyFamily) are integers; system selection uses a stable string SystemId.

Unknown engineering values are nullable or explicitly marked NOT PROVIDED. Public model defaults create containers and identity/presentation defaults, not capacity, speed, rope specifications, CW clearances or manufacturer assumptions. A ShaftMaster new project is filled from the editable preset library instead (`FollowsPresets = true`; see `PRESETS.md`). Only the currently accepted `traction-geared` / `ExistingPlan` / `existing-plan-v1` combination is enabled. Other system IDs are a future catalog extension and currently return validation failure. DriveType and per-floor landing-door settings are metadata, not new geometry capabilities.

Floors are normal physical landings. Each retains FloorId independently of Name and IsServed. `HeightToNextMm` is the authoritative interval to the next normal floor; the last normal floor has null. Lowest normal FFL is zero. `ProjectFloors.Elevations` cumulatively calculates elevations. Inserting before an intermediate floor shifts it and higher floors by the new interval. Removing that inserted floor removes its following interval. Rename never changes FloorId. Changing the displayed car FloorId requires a served landing. NO STOP retains floor height/FFL/slab and removes the native landing door through the existing updater.

Structural R is not an independently entered normal floor. Its elevation is highest served FFL + OH + measured MR slab thickness. Legacy R identity/name are retained as migration metadata so its source identity is not lost. A-A's canonical landing thickness 250 and the coordinated MR slab thickness are different concepts.

Car/CW absolute reference pose is explicit and provisional. Motion remains 1:1, deltaCW=-deltaCar; floor count never substitutes for CW calibration. Pit, OH and bracket maximum are nullable until a real project/migrated A-A provides them. A-A's old initial UI defaults remain in the legacy command for compatibility.

## Results and context

`ElevatorDesignEngine.Calculate(project, context, views)` delegates to the unchanged DesignRules, MachineRoomRules, MachineRoomSectionRules/ReevingSolver and SectionAACalculator. `DesignContext` carries reviewed template inputs: equipment profile, measured CW depth, measured room margins, B-B SectionReference, support offsets and retained deflector geometry. These values are not secretly supplied by the UI.

`ElevatorDesignResult` holds existing ElevatorParameters, A-A geometry, floor elevations and structured validation. Car DBG/width/depth, TZ, door/CW selection, governor offset, deflector selection, room dimensions and reeving geometry are outputs, not duplicate input fields. Approved native V1 vertical dimensions/profiles are exposed as result metadata. Supporting existing DWG design records remain result caches.

ValidationIssue provides Code, Field, Message, typed Status and BlocksGeneration. A normal engineering warning or component-code FAIL does not imply that geometric drawing generation must be blocked. LayoutStatus, WrapAngleStatus and CodeDiameterRatioStatus are independent. Missing speed/rope/clearance data remains explicit. Unsupported geometry or incompatible floor intervals blocks generation rather than substituting equipment.

## DWG compatibility and synchronization

The existing `ELEVATOR_AUTOMATION/Project` record remains the ProjectInput compatibility projection. The versioned unified envelope is stored alongside it at `ELEVATOR_AUTOMATION/ElevatorProject`. SectionAAProject remains the A-A compatibility projection. Existing binding, audit and result record names stay intact.

UnifiedProjectStorage.Read loads a unified document if present; otherwise it migrates Project + SectionAAProject in memory. It does not mutate drawings merely by reading them. Save writes the unified envelope and both relevant compatibility projections in the caller's DWG transaction. R is recalculated from the actual section slab when present, so a no-change save does not invalidate A-A's manifest.

Existing commands still write Project or SectionAAProject. ProjectDataStorage.Write now synchronizes those writes into the unified model in the same transaction. It retains unified-only fields and stable identities. Unsupported unified versions prevent legacy edits from silently overwriting newer project data. There is no timestamp-based last-writer guessing and no UI-owned engineering copy.

Migration precedence: current A-A floor stack/Pit/OH/display/reference-pose data governs those fields; legacy Project governs shaft/machine/rope/metadata fields. Legacy Stops/Travel/FloorHeights are preserved as migration metadata only when no real floor stack exists. Once a floor stack exists, those legacy summaries are derived on projection. Unknown Extensions are retained. A pending project change may correctly make geometry stale until regeneration; storage itself does not secretly move entities.

## New API usage

The future UI can reference `IProjectDrawingGenerator`, ElevatorProject, GenerationOptions and DrawingGenerationResult from Core. The AutoCAD host binds a Document to `new ProjectDrawingService(document)`. Calls are made in the AutoCAD document/command execution context; the adapter owns document locks and database operations. A future out-of-process UI still needs a host transport/scheduler, not command-string automation.

Default GenerationOptions.Views is All (Plan, MachineRoomPlan, SectionAA, SectionBB). Dependent views update prerequisites in Plan→MR→B-B→A-A order. Existing placements are retained by default; ArrangeViews opts into presentation-only translation. Newly imported views trigger automatic arrangement. OutputPath is optional, and the service refuses to overwrite an existing file. A reviewed Plan template/project document is the starting point; missing MR/B-B/A-A views are imported from their approved masters.

The API performs geometric calculations before updating existing views. Template import and source dimension-association detachment occur in an earlier adapter stage; if later design validation fails, imported views can remain in the working document. The future UI should use a new project document and publish/save only a successful result. Whole-operation document rollback/publication belongs to the future application host and is not claimed as implemented here.
